                    - heading "What Problem This Solves" [level=2] [ref=f37e254]
                    - paragraph [ref=f37e255]: Fixes an issue where a terminal opened through the Gateway MCP loopback could survive its task's completion when another child session had a task with the same run ID.
                    - paragraph [ref=f37e256]: "Gateway tool resolution dropped the prepared run ID. Forwarding it exposed a second issue: terminal ownership used the registry's global preferred run-ID match, then discarded a mismatched child session without searching the correct scope."
                    - heading "Why This Change Was Made" [level=2] [ref=f37e257]
                    - paragraph [ref=f37e258]:
                      - text: The Gateway now forwards its existing prepared
                      - code [ref=f37e259]: runId
                      - text: . Terminal ownership resolves the task through the canonical task-registry scope
                      - code [ref=f37e260]: "{ runId, childSessionKey }"
                      - text: ", then records the exact private task ID used by lifecycle cleanup."
                    - paragraph [ref=f37e261]: This is the complete owner-boundary repair. It adds no config, protocol, SDK, migration, persistence, identity, fallback, or cache surface. The detached-task runtime retains its existing global lookup because it has a different ownership contract.
                    - paragraph [ref=f37e262]: This change was developed with AI assistance and rewritten by a maintainer after ClawSweeper found the cross-child collision.
                    - heading "User Impact" [level=2] [ref=f37e263]
                    - paragraph [ref=f37e264]: Completing one Gateway/loopback task now closes that task's PTY even when another child session reuses the same run ID. The sibling task's terminal remains live and writable.
